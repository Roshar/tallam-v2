# Правила разработки Tallam v2

Договорённость проекта: **каждая новая фича документируется**, а любые доработки делаются **с минимальным вмешательством в существующий код**. Ниже — как это применять на практике.

## Четыре документа и их роли

| Документ | Отвечает на вопрос | Когда обновлять |
|---|---|---|
| [`PROJECT.md`](../PROJECT.md) | Как устроен проект и что уже сделано | Когда меняется состояние или структура проекта |
| [`docs/FEATURES.md`](FEATURES.md) | Какие фичи есть, где они живут и как их проверить | **На каждую новую фичу** |
| [`docs/ARCHITECTURE.md`](ARCHITECTURE.md) | Прод, сервер, бэкапы, восстановление | Когда меняется инфраструктура |
| [`docs/CONVENTIONS.md`](CONVENTIONS.md) | Как мы работаем (этот файл) | Когда меняется сам процесс |

Документы не дублируют друг друга. `FEATURES.md` — каталог: одна запись на фичу. `PROJECT.md` — связный рассказ о состоянии. Если фича меняет общую картину, обновляются оба.

## Правило 1. Каждая фича документируется

**Фича** — это новая страница, раздел, эндпоинт, таблица, интеграция или заметное изменение поведения. Опечатки, правки текстов и косметика записи не требуют.

**Фича не считается сделанной, пока не добавлена запись в [`docs/FEATURES.md`](FEATURES.md).**

Шаблон записи (копировать целиком):

```markdown
### Название фичи
`✅` · введено `<commit>` (<дата>, <инструмент>)

- **Что:** одно-два предложения о смысле и поведении. Без пересказа кода.
- **Где:** `путь/к/странице.tsx`, `путь/к/сервису.ts`, `GET|POST /api/...`, таблица `имя_таблицы`
- **Проверка:** конкретные шаги, как убедиться, что работает.
- **Ограничения:** чего фича не делает, если это важно для контекста.
```

Поля `Статус` — `✅` готово, `🚧` в работе, `📋` план. Если фича менялась позже, в запись добавляется строка `- **История:** <commit> — что изменилось`.

### Definition of Done

Фича закрыта, когда выполнено всё:

1. Код собирается: `npm run build` без ошибок.
2. Проверено локально: вход `test@test.ru` / `123456` → нужный раздел работает.
3. Проверены **соседние разделы**, которые могли задеть правки.
4. Добавлена запись в `docs/FEATURES.md`, при необходимости обновлён `PROJECT.md`.
5. Коммит с осмысленным сообщением и трейлером инструмента (см. ниже), запушен в `origin/main`.
6. Деплой — только по согласованию с владельцем (см. «Деплой»).

## Правило 2. Минимальное вмешательство

Цель — не ломать то, что уже работает у школ. Правила жёсткие:

1. **Новая фича — новые файлы.** Страница, сервис, контроллер, стили создаются заново.
2. **Существующие файлы трогаем только в точках регистрации.** Это исчерпывающий список «разрешённых» правок:
   - `frontend/src/App.tsx` — новый роут;
   - `frontend/src/components/SchoolCabinetLayout.tsx`, `frontend/src/components/AdminCabinetShell.tsx` — пункт навигации;
   - `frontend/src/api/client.ts` — метод API;
   - `frontend/src/types/*.ts` — типы запросов и ответов;
   - `backend/src/index.ts` — монтирование роутера и `ensure*Schema`;
   - `backend/src/routes/*.routes.ts` — регистрация маршрутов. Если файл растёт, новый раздел выносится в отдельный роутер и монтируется, как `accountantRoutes` на `/api/status`;
   - `backend/src/services/audit-log.service.ts` — новая строка в реестре `AUDIT_ACTIONS`, иначе действие не попадёт в фильтр журнала;
   - **страница-хозяин** — существующая страница, на которой появляется кнопка, ссылка или блок. Правка только аддитивная: добавить элемент и обработчик, не переписывать разметку вокруг;
   - **стили** — только добавление новых классов, существующие правила не меняем.

   Контроллеры и сервисы в этот список не входят: фича приносит свои файлы, даже если рядом уже лежит похожий контроллер.
3. **Никаких попутных рефакторингов.** Увидел грязь рядом — не чини в этом коммите. Отдельный коммит, отдельное согласование.
4. **API только аддитивно.** Существующие эндпоинты не меняют форму ответа и поведение. Нужно поменять — предупредить владельца и описать изменение в записи фичи.
5. **Перед правкой общего файла** (сервис, компонент, общий CSS) — найти всех потребителей (`grep`) и проверить, что они не сломаются. Особенно: `frontend/src/api/client.ts`, `frontend/src/styles/admin.css`, `backend/src/services/card.service.ts`, `backend/src/services/auth.service.ts`, `frontend/src/components/Layout.tsx`.
6. **База только аддитивно.** Новые таблицы — через `ensure*Schema` в сервисе **и** файл `database/init/NN-описание.sql`. Существующие таблицы, колонки и типы не меняем и не удаляем без явного согласия: та же схема используется прод-базой.
7. **Прод-данные не трогаем при разработке.** Локальная база — Docker `:3307`. Запись в прод `tallam_v2` и в Beget-базу v1 (исторический источник) запрещена.
8. **Старая версия v1 закрыта** (11.10.2026): процесс `index` остановлен, `old.tallam.ru` перенаправляет на `tallam.ru`. Код `/home/app` и база Beget не удалены, но поднимать v1 и возвращать проксирование без явной просьбы владельца нельзя — как и удалять их.

## Порядок работы над фичей

```text
1. Контекст     прочитать PROJECT.md и релевантные записи FEATURES.md
2. Реализация   новые файлы; существующие — только точки регистрации
3. Проверка     npm run build + смоук локально + соседние разделы
4. Документация запись в FEATURES.md (+ PROJECT.md, если изменилась картина)
5. Коммит       осмысленное сообщение + трейлер, push в origin/main
6. Деплой       по согласованию, по шагам ниже, с проверкой после
```

### Коммиты

- Сообщение — по-английски, в повелительном наклонении, одна строка-заголовок и тело с объяснением **почему**, а не «что».
- Трейлер инструмента в конце: `Co-authored-by: DeepSeek Harness` или `Co-authored-by: Cursor`. По нему восстанавливается, чем велась разработка.
- Один коммит — одна законченная мысль. Документация фичи идёт в том же коммите, что и код.

### Деплой

Автодеплоя нет, но и собирать на сервере **не нужно**: у VPS ~1 ГБ памяти, сборка упирается в предел, а ядро при нехватке памяти убивает не сборку, а самого крупного потребителя — MariaDB. Поэтому артефакты собираются на ноутбуке и привозятся готовыми:

```bash
npm run deploy
```

Скрипт [`scripts/deploy.sh`](../scripts/deploy.sh) делает всё по шагам: проверяет, что рабочее дерево чистое, собирает `backend/dist` и `frontend/dist` локально, тянет исходники на сервере через `git pull --ff-only`, при смене `package-lock.json` догоняет зависимости через `npm ci`, складывает текущую сборку сервера в `/var/backups/tallam/dist/`, везёт артефакты через `tar` по ssh (локальный rsync — это openrsync с урезанными возможностями, зависеть от него не хотим), перезапускает только `tallam-v2` и проверяет health и хеши ассетов.

- nginx перезапускать не нужно: он отдаёт `frontend/dist` с диска.
- Процесс `index` (v1) остановлен; скрипт его не касается и не поднимает.
- Документация и прочие правки без кода деплоя не требуют: достаточно `git pull` на сервере.
- **Откат:** вернуть сборку из `/var/backups/tallam/dist/{backend,frontend}-<штамп>` и `pm2 restart tallam-v2 --update-env`. Либо `git reset --hard <предыдущий-коммит>` и деплой заново.
- Перед деплоем стоит убедиться, что офсайт-бэкап свежий: `npm run backup:fetch`.

Аварийный путь, если под рукой нет ноутбука (помнить про память: прижать heap, чтобы сборка упала явно, а не утянула базу):

```bash
ssh root@185.207.0.41
cd /home/tallam-v2 && git pull --ff-only origin main
NODE_OPTIONS=--max-old-space-size=384 npm run build
pm2 restart tallam-v2 --update-env
```

На сервере включён swap на 2 ГБ (`/swapfile`, `vm.swappiness=10`) — это подушка на случай пиков, в том числе для MariaDB.

## Чего не делать

- Не коммитить `.env`, SQL-дампы, `school-passwords.log` (см. `.gitignore`).
- Не менять `SUBSCRIPTION_DATA_ENCRYPTION_KEY` на живой базе — старые заявки перестанут читаться.
- Не считать дамп на самом VPS достаточным бэкапом: вместе с сервером он исчезнет.
- Не «улучшать» форму оценки и проектный профиль учителя в сторону карточного редизайна: они намеренно повторяют табличный стиль v1.
